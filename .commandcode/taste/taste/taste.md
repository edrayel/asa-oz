# Taste
- When a review/audit surfaces a concrete problem (a code finding, or an agent-highlighted design smell such as two controls doing the same job), expects it to be acted on once approved ("Proceed with fixes"; "I am granting you to proceed with reconciling and fixing it") rather than stopping at a recommendations report. Confidence: 0.75
- Wants shared, reusable components (header, footer, etc.) instead of duplicated static markup repeated across pages — "it doesn't make sense for these to be static and raw." Explicitly requires the shared header/footer to render identically across ALL pages (only the active nav link may differ) and to come from a single shared source (shared.js + shared.css) rather than per-page markup or CSS. Confidence: 0.98
- When a queue of previously identified follow-up/pending items exists, expects them all to be completed in the same pass once approved ("Yes, build a shared header/footer. Then fix all pending queued items.") rather than left dangling for a later session. Confidence: 0.7
- Wants the agent to debug reported issues independently and verify with its own evidence ("Debug and see for yourself", later reiterated as a terse "Debug and fix") rather than asking the user to explain or re-check — expects the agent to trace the served output vs. local files and pinpoint root causes itself. Confidence: 0.8
- Before implementing a requested feature, expects the agent to first review the codebase for whether it is already implemented versus missing (e.g., "I can't recall if its already implemented so review it") and to report a clear existing-vs-gap breakdown before changing anything — don't rebuild what exists, and surface what's genuinely missing.
- Drives multi-part work with terse one-word nudges ("Continue") — when a session resumes mid-task (e.g., after an investigation-heavy turn that ended without finishing the edits), the user expects the agent to proceed straight through implementation and verification without re-confirming scope, re-reading instructions, or re-asking what to do. Confidence: 0.6
- For audit/hardening work, prefers the agent to deliver concrete verdicts (line numbers, file paths, severity) backed by exact code snippets rather than abstract recommendations — wants actionable findings that can be turned into edits without further interpretation. Confidence: 0.85
- Wants the agent to investigate before proposing — opens every audit by spawning parallel `explore` subagents to map routes, content, integrations, and risks (architecture, CMS, Drive, SEO/design/ads) before designing the plan, instead of relying on a single read-through of the code. Confidence: 0.8
- Before starting multi-phase work, presents the user with concrete decision points via multi-choice prompts (Build path, Ads scope, Security scope, Drive role) and picks one option per question with `(Recommended)` labels where appropriate — uses these prompts to lock in scope before writing the plan rather than iterating on plan content. Confidence: 0.85
- When restructuring pages to eliminate redundancy (e.g. moving home sections to About), expects the agent to check in first with an explicit list of what will be removed/moved before editing. Confidence: 0.7
- For non-trivial cleanup/fix work the agent has flagged but left undone, expects a written plan proposed for approval before implementing ("Propose a plan to fix the two things you left alone") — the plan should cover the approach, ordered per-file steps, risk/reversibility, and concrete verification steps, and the user approves the plan (resolving any genuinely ambiguous fork via a decision prompt) before edits begin. Confidence: 0.65
- For non-trivial refactors/redesigns the user explicitly asks the agent to plan before executing ("Plan it well before executing") — expects plan-mode style work first (explore what exists, describe the design, ordered per-file steps, verification plan, plus honest open questions) and approval before any edits are made. Confidence: 0.7

- Before operations that could affect production state (push, deploy, restart), expects the agent to proactively preserve local copies of production data (e.g., database dumps) and confirm those artifacts are git-ignored / excluded from the push — treats data-loss prevention as part of the pre-flight, not an afterthought. Confidence: 0.6
- When asked for "percentage completion and readiness" / production-readiness assessments, expects a categorized percentage breakdown (per area: structure, security, DB, testing, monitoring, etc.) plus a single weighted overall %, a short "top blockers" list, and a "what's already excellent" callout — wants the answer structured so the user can scan it and see both the headline number and what sits behind it, not a prose essay. Confidence: 0.85

- Requires site content to be CMS/DB-managed, never hardcoded in templates or static HTML — explicitly states "The site is meant to be CMS-managed and not static HTML-hardcoded." New or edited content should be persisted into the content store (e.g., `page_sections` rows) so it is editable via the admin without a code change or restart, rather than left as code-only defaults; when content is served, be ready to explain which layer (CMS schema default vs stored DB row vs template) it actually comes from. Confidence: 0.85

- Prefers one control per behaviour in admin/CMS settings: when two controls have the same effect (e.g. a price toggle plus a duplicate Price display Public/Hidden select), wants them reconciled into a single source of truth rather than left as ambiguous duplicates. Extends to controls that save but do literally nothing — prefers removing no-op settings outright (key, admin form row, and save-handler special-case) rather than leaving dead controls or building them out, so the admin only ever holds controls that actually change behaviour. Confidence: 0.7

- Treats pushing to origin as a deployment-triggering action that should be deferred until the implications (rebuild, ephemeral disk wipe) are fully understood — explicitly says "don't push yet" even when a push seems like the natural next step, preferring to investigate branch state and data-loss risk first. Confidence: 0.75
- Expects honest pushback and genuine consultation rather than mechanical compliance: when asked to move, remove or reshape something, wants the agent to say whether it is actually the right call and to brainstorm the underlying problem ("should it really feature on the about page?", "We need to brainstorm the reason the site owner feels so", "Thoughts?"). Values a reasoned recommendation (which can be forwarded to the site owner/stakeholder) over obedient execution. Confidence: 0.75
- Reports design/layout problems by pasting the rendered HTML of the offending sections (with their live classes and copy), expecting the agent to map each snippet back to its template/CSS and fix it consistently across pages. Confidence: 0.65
